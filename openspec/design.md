## Context

See proposal.md for motivation. Same constraints as the Go and Python SDKs (see the equivalent `go-sdk`/`python-sdk` changes): hush-hush's `api/openapi.yaml` is spec-first, linted but not semantically drift-checked; no real API-version concept; auth is a static bearer token on write paths only, plus an optional unverified `X-Caller` header.

## Goals / Non-Goals

**Goals:**
- A deterministic, mechanically regenerable client.
- Idiomatic TypeScript: `Promise`-based methods, `async`/`await`, no `any` in public signatures.
- A clear generated/hand-written boundary that survives regeneration.
- A regeneration pipeline that surfaces breaking spec changes via classification, even without gating merge.

**Non-Goals:**
- OAuth2 support — hush-hush only has a static bearer token.
- A unified cross-language docs site.
- Any change to hush-hush's server or its spec.
- Implementing Pact provider verification inside hush-hush's own CI.
- Automating the npm publish step — deliberately manual, tracked in hush-hush issue #76.

## Decisions

**Generator: `openapi-typescript` for types only, hand-written client on top — not a hosted platform or a generated full client.** `openapi-typescript` produces exact, well-maintained TypeScript types from a spec with no runtime dependency; it deliberately doesn't generate a client, which fits this project's existing decision to hand-write the transport/retry/error layer anyway rather than trust a generated client's idiom. Hosted platforms (Speakeasy/Fern/Stainless) rejected project-wide in favor of free OSS tooling.

**Transport: native `fetch`, no HTTP library dependency.** Node 22+ (this SDK's floor) has stable native `fetch`; adding `axios` or a similar dependency would be extra surface area and a supply-chain dependency for something the runtime already provides.

**Generated/hand-written boundary via header comment.** `openapi-typescript`'s output is a single `.d.ts`/`.ts` types file carrying `// Code generated by openapi-typescript; DO NOT EDIT.`. The hand-written client imports these types but never edits the file; a CI check fails if the generated file's diff isn't purely mechanical regeneration output.

**Spec pinning via git submodule**, same approach as the other SDKs: the submodule's pinned commit is the version record; the generated types file additionally states the pinned commit as a comment for human readability.

**Versioning via spec diff.** `openapi-diff` compares the current pinned commit against the one the last release was generated from and classifies the change as additive or breaking, driving the semver bump.

**Merge policy: full auto-merge for this session, scaffolding and all regeneration PRs alike** — an explicit, repeated grant from Ryan, given after being shown the risk that a breaking spec change can produce a small, green-CI-passing diff. The `openapi-diff` classification still runs and is surfaced on every PR for visibility; it doesn't gate merge.

**Auth: bearer token in the constructor with an `HUSH_HUSH_API_KEY` env var fallback; `X-Caller` as a per-call option, not client-level config.** Same reasoning as the other SDKs: the token is only required on write paths, and `X-Caller` attributes a specific call, not a client instance.

**Retry: network failures, 5xx, and 429 only; exponential backoff with jitter; honor `Retry-After`.** Never retry other 4xx.

**Errors: a typed error class hierarchy (`HushHushError` base, `APIError` subclass) extending `Error`**, carrying status, an optional request-ID property (populated when a documented header is present, empty otherwise), and the parsed error body — never a bare string or the raw `Response`.

**Audit log: a plain typed query method, not an iterator.** hush-hush's `/audit-log` has no pagination parameters (checked directly against the spec) — it returns a flat array for the given filters, so `client.auditLog.query(filters)` resolves with the full result set rather than exposing an `AsyncIterable` over pages that don't exist.

**Packaging: npm, ESM-first with a CJS fallback build** for broadest consumer compatibility; publishing to the npm registry is a manual maintainer step, not CI-automated, per hush-hush issue #76.

## Risks / Trade-offs

- [`openapi-typescript` generates types only, so more of the client is hand-written than a full-client generator would produce] → accepted, since the transport/retry/error layer was always going to be hand-written regardless of generator choice; this just means the same is true for request-building glue.
- [Full auto-merge applies to all regeneration PRs, so a breaking spec change can auto-merge as a small diff] → accepted risk, per Ryan's explicit repeated auto-merge grant. `openapi-diff`'s classification remains visible after the fact even though it doesn't block.
- [ESM/CJS dual packaging adds build complexity] → mitigated by using a standard bundler config (tsup or equivalent) rather than hand-rolling two build pipelines.
